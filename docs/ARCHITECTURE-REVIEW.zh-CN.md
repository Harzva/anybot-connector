| 意见 | 决策 | 理由及验收 |

| 收缩为文字 HTTP/reference 的最小闭环 | 采纳顺序，MCP 与渠道分片跟进 | 先验证基础事实，再用独立客户端验证跨入口 |

| 不静默哈希 requestKey | 采纳透明性，校正实现 | 为防跨调用方碰撞，公开定义 SHA256 命名空间映射，保留原 requestKey；不伪称直接透传 |
| 企业归属默认拒绝 | 采纳 | 必须受信操作者显式绑定；不把发布健康检查当作企业归属证明 |
| cancel、abort、关闭必须分别表达 | 采纳 | provider 终态决定结果；断连不自动取消、重提 |
| 无真实访客身份时独立请求上下文 | 采纳 | 文字历史作为不可信输入；拒绝自报 system/developer 权限 |
| 冻结共享接口和文件所有权 | 采纳 | 公共 API 见 0002；原生实施者各自独占模块 |
| Knocket 不作为 alpha 真平台门槛 | 采纳 | 严格文字子集可实现；真实平台、接管和真实逐 token 流保持待验 |

最小实现 API 已冻结在 [0002](../spec/0002-alpha-api.md)。原 RFC 的要求仍适用；
alpha 明确不提供分布式运行、自动 POST 恢复重放、输入续接或事件流。
架构建议不等同于实现验收；实际结果记录在后续验收报告中。

## 后端验收追加评审

2026-10-26 通过现有 CXF `deepseek-flash / low` 与 CXQwen
`qwen3.8-flash / medium` 分别取得实际原生回复；后者沿用既有 Qwen Token Plan
路由，没有新建账号或 API 通道。执行回执只证明配置路由完成，不独立证明服务端模型身份或计费。

两者均指出 TeamBot 的 6000 UTF-16 单元限制与核心通用 20000 字节限制不同。
协调者采纳 provider 声明与核心派发前校验，补充中文、emoji、完整聊天历史、拒绝后
原键可用的边界测试；同时核对上游空白/NUL 规则。没有把所有上游 4xx 擅自解释为未执行。

采纳“带明确 operator binding 的隔离后端验收可以继续”，并保留企业成员验证与发布归属
缺乏联合证明的限制。校正 CXF 建议中的 `live-platform-verified (isolated)` 标签：本项目
仍记为隔离后端验收，不能用于真实平台通过声明。共享凭据不证明访客身份；独立会话不替代
访客 ACL。状态检查的撤权能力须由真实上游拒绝行为支持，不能仅依据匹配的发布 ID 推断。
真实 Knocket 字段、重试、访客身份和人工接管保留为后续平台门槛；用户确认真实入口稍后提供。

实际后端随后发现：TeamBot 查询要求服务签发的 opaque receipt，而非提交时的 requestId。
针对这一具体差异，CXF/CXQwen 又分别完成一轮只基于精简证据的咨询。采纳核心私有日志
保存回执、明确 `lookupByRequestId` 能力、无回执时不查询伪 ID 或重发 POST。
采用 CXQwen 对默认能力的收紧建议：新 provider 必须明确声明恢复能力，缺失即拒绝。

协调者校正：回执只能来自受信配置的 adapter 响应，外部调用者不能写 snapshot 或导入回执；
后续查询须与保存的 ID 完全匹配。现有发布凭据仍是上游授权前提，不能把回执单独描述为
完整 bearer 授权。保存于私有日志供实际查询，不能仅存不可逆摘要。没有采用“丢失日志后
重算公共句柄”的建议：损坏日志必须停止，不能重建缺失授权事实或绕过原持久化门槛。
丢失提交响应或回执落盘前崩溃的窗口明确不可自动恢复，须可信操作员核查；不声称已执行取消。
