# 实施拆分与协作任务书

状态：CXF 实际审阅已完成，公共 API 已冻结。原生 Kimi 已实际实施协议、渠道、示例与独立互操作测试。ZCode 原生 CLI 无法解析现有 Coding Plan 模型，未发生其实施调用；用户随后明确授权协调者接手 core/providers，现由协调者完成核心、提供方、CLI 和最终集成验收。详见 STATUS.md。

## 1. 执行顺序

1. 协调者核对当前仓库、WIP、工具入口与文件归属，向 CXF 发起一轮有界架构审阅。
2. 收到实际回复，记录采纳 / 校正 / 暂缓意见，冻结最小 contract。
3. 协调者建立 package、lockfile、测试运行方式和公共类型边界。
4. ZCode 原生入口未能解析模型；用户授权协调者接手核心与 provider，Kimi 按已冻结 contract 独立编写黑盒用例。
5. Kimi 实施 HTTP/MCP 和首个渠道子集，并用实际 TeamBot 后端辅助隔离验收。
6. 协调者审查、合并、运行交叉测试与干净环境 quickstart，修复问题，再进入真实平台试点。

本地已安装命令、账号缓存、dry-run 都不代表模型已经执行。账号或额度无法确认时，记录准确阻塞，不更换付费 API 或冒用另一模型名称。

## 3. 文件所有权

| 责任人 | 独占范围 | 允许只读的相邻内容 |
| --- | --- | --- |
| 协调者 | 根 package / lockfile / CI、`spec/`、公共文档、最终集成和发布 | 全仓库；私有产品仅按授权核对接口 |
| 协调者（用户授权接手原 ZCode 工作包） | `src/core/`、`src/providers/`、`test/core/`、`test/providers/` | 已冻结 contract、共同 fixtures 的约定 |
| Kimi | `src/transports/`、`src/channels/`、`test/transports/`、`test/interoperability/`、`examples/` | Core / provider 的公共接口 |
| 协调者首轮负责 | `src/cli/`、`test/fixtures/` | 各模块的可用契约 |

任何共享文件更改先交给协调者。两位实施者都必须知道“仓库中还有其他贡献者，不回滚、不覆盖别人的修改”；不要通过整树复制或 reset 解决冲突。

## 4. CXF — 架构审阅任务

输入：本方案、RFC、已观察到的接口边界摘要、首版目标、现有协议来源、下方验收门槛。默认一轮，只有影响实现的重要分歧才针对性追问。

要求回答：

- 按严重程度列出最多八项会阻断首版的设计问题，指出具体章节。
- 区分可复用标准、只需薄适配的部分和确有必要新增的部分。
- 裁决任务状态归属、持久幂等、撤权和结果未知的语义。
- 检查 TeamBot 归属验证与渠道最终用户身份是否被错误合并。
- 推荐最小可交付切片，说明延后功能及理由。
- 检查 ZCode / Kimi 分工，指出共享文件和依赖冲突。

输出是建议，不能替代源码验证。协调者创建 review decision 文档，保留不同意见和未核实假设；原始会话与本机路径保留在仓库外。

## 5. 原 ZCode 工作包 — 已授权协调者接手

以下 Z1–Z3 保留原工作包编号，实际实现者是协调者，不能据编号归功于 ZCode。

### Z1：核心合同实现

依赖：CXF 决策、冻结 contract、工程初始化。

交付：严格输入校验、能力检查、可信固定路由、授权回调、规范错误、幂等命名空间和恢复策略。不得自己实现新模型执行器、企业登录或通用工作流引擎。

验收：同键不同载荷冲突、跨主体不可见、越权直接调用被拒绝、撤权阻止迟到结果、未知提交不重发、非法上游响应不变成成功。

### Z2：参考提供方

交付：可重复控制的 queued/running/terminal、取消与故障注入；所有模型输出明确标注为夹具。支持测试重启恢复所需的持久状态，但不访问真实个人或企业资料。

验收：进程重启、并发重试、超时后查询、取消竞争和状态顺序由行为测试验证。

### Z3：TeamBot adapter

交付：对已确认 API 版本的 describe/submit/get/cancel 映射，授权接点、限制和错误转换。仅使用目标服务的窄接口；公开仓库不导入私有产品包或复制私有源码。

验收：合成 HTTP 服务覆盖协议错误；真实企业集成由协调者在独立且授权的环境验证。若企业发布归属缺少可验证声明，明确记录限制并阻断不成立的自动验证路径。

最终回报：变更文件、实际命令及结果、未实现项、依赖/许可证变化、需要协调者决定的事项。禁止宣称仅由 mock 证明生产就绪。

## 6. Kimi — 绑定、场景与独立验证

### K1：黑盒一致性测试设计

依赖：冻结 contract；可与 Z1 并行。

交付：从 RFC 独立推导的验收用例、HTTP/MCP 行为映射、公共 fixture 需求清单。测试先约束外部结果，不复制 ZCode 内部算法断言。

### K2：HTTP 与 MCP

依赖：Core / provider 接口稳定。

交付：有界 HTTP 输入与错误映射，使用官方 MCP SDK 的四类操作，认证/授权接点，安全关闭。协议版本和 SDK 版本在锁文件与支持矩阵记录。

验收：官方 MCP 客户端端到端调用；同一 caller/request 从 HTTP 提交再由 MCP 查询/取消，结果和权限一致；transport 不能绕过 core。

### K3：Knocket 文字子集

依赖：K2 与 TeamBot provider 合同完成。

交付：模型别名固定路由、文字 messages 验证、普通响应及诚实声明的流式能力、超时/断连/重试策略。已知不支持字段要明确拒绝，不能静默删除。

验收：受控请求样本覆盖后，等待真实账号验证才能标记 Knocket 支持。人工接管没有平台回执时不得返回“已完成接管”。

最终回报与 ZCode 相同，并注明独立测试发现的问题、是否已修复、哪些必须交还相应文件 owner。

## 7. 协调者验收与发布职责

- 核对实际 agent 回执、变更与测试，不以任务派发为完成。
- 保持主产品 WIP 与本仓库隔离；TeamBot 宿主接线另作窄范围文件交接。
- 运行跨模块测试和公开 checkout quickstart，核对无私有依赖。
- 审核公开内容、来源、许可、包文件清单和 CI 日志。
- 更新支持矩阵与状态，发布真实达到的阶段；实际平台待验时保留该限制。
- 对不确定的原生 agent 调用先查原会话状态，不自动重启同一有副作用任务。

## 8. 决策记录模板

每个重要决策记录：问题、事实与来源、CXF 建议、采纳/校正/暂缓、理由、实现文件、验证证据、剩余限制。没有实际 CXF 回复时只记录“待审”。
